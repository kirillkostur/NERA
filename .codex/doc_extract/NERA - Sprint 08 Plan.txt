NERA — Sprint 08 Plan
First Playable QA + Optimization Baseline
1. Назначение Sprint 08
Sprint 08 нужен, чтобы зафиксировать техническое состояние First Playable.
После Sprint 07 у нас уже есть:
рабочий loop
понятные цели
feedback
атмосфера
placeholder VFX
placeholder audio
terminal polish
Expedition 01 readability pass
Sprint 08 не должен добавлять новые фичи.
Его задача:
проверить стабильность
→ измерить производительность
→ найти критические баги
→ зафиксировать baseline
→ подготовить First Playable к lock
2. Главная цель спринта
Цель
Сделать первый технический QA-pass First Playable.
Нужно проверить:
полный проход игры;
стабильность сцен;
стабильность UI;
стабильность input/cursor;
FPS baseline;
memory baseline;
build size baseline;
scene loading;
LOW preset assumptions;
критические баги;
must-fix список перед First Playable lock.
Главный результат:
мы понимаем, в каком техническом состоянии находится First Playable
3. Почему это важно
До Sprint 08 игра может “работать у нас в редакторе”.
Но First Playable должен работать как билд.
Проблема:
Editor скрывает часть проблем
В билде могут проявиться:
неработающие scene transitions;
сломанный cursor lock;
потеря input после UI;
пустые ссылки;
неправильные Build Settings;
missing assets;
сильные просадки FPS;
долгие загрузки;
большой размер билда;
проблемы LOW-настроек.
Sprint 08 нужен, чтобы поймать это до First Playable Lock.

5. Главный принцип Sprint 08
Sprint 08 — это не “делаем красиво”.
Sprint 08 — это:
измеряем
→ фиксируем
→ исправляем критичное
Правило:
Если проблема не мешает First Playable и не ломает baseline — не трогать сейчас.
6. QA Priorities
6.1. Priority 1 — Blocker
Баги, которые полностью ломают прохождение.
Примеры:
игра не запускается;
билд не собирается;
сцена не загружается;
игрок не появляется;
терминал не открывается;
дрон не открывает Expedition 01;
невозможно вернуться на станцию;
невозможно завершить research;
input полностью ломается;
save/load ломает состояние.
Blocker должен быть исправлен в Sprint 08.
6.2. Priority 2 — Critical
Баги, которые сильно мешают прохождению, но игру можно пройти обходным путём.
Примеры:
UI иногда не закрывается;
cursor остаётся видимым в gameplay;
objective не обновляется;
prompt не появляется с первого раза;
объект можно собрать дважды;
Library не всегда обновляется;
Translation Level не обновляется визуально;
после возврата игрок появляется в неудобной точке.
Critical желательно исправить в Sprint 08.
6.3. Priority 3 — Major
Баги, которые заметны, но не ломают core flow.
Примеры:
текст криво выровнен;
VFX слишком яркий;
звук повторяется слишком часто;
light pop заметен;
небольшие просадки FPS;
debug text остался в UI;
неидеальная навигация в терминале.
Major можно исправлять, если осталось время.
6.4. Priority 4 — Minor
Мелкие проблемы.
Примеры:
typo;
некрасивый placeholder;
слабый материал;
мелкий clipping;
неидеальный fade;
временная иконка.
Minor не должен съедать Sprint 08.
7. Full Playthrough QA
7.1. Проверяемый flow
Проверить полный flow с нуля:
Start on Station
→ Restore Power
→ Open Terminal
→ Launch Drone
→ Discover Expedition 01
→ Travel to Expedition 01
→ Explore Ancient Outpost
→ Read Ancient Record
→ Inspect NERA Memory Core
→ Notice IO Trace
→ Return to Station
→ Analyze NERA Memory Core
→ Library Updated
→ Translation Level: Fragmented
→ New Objective Hint
7.2. Правило теста
Проход должен быть выполнен:
без debug-кнопок
без ручных действий в Editor
без перезапуска сцены
без изменения Inspector
Если без debug пройти нельзя — это blocker.
8. Build QA
8.1. Что проверять в билде
Проверить:
билд запускается;
окно открывается корректно;
mouse lock работает;
keyboard input работает;
UI input работает;
Esc закрывает fullscreen UI;
сцены загружаются;
save file создаётся;
load работает;
reset работает;
игра закрывается без ошибок.
8.2. Build Settings
Проверить, что в Build Settings есть:
Station_FirstPlayable
Expedition_01_FirstPlayable
Если будет MainMenu позже — добавить отдельно.
На Sprint 08 MainMenu не обязателен.
9. Input / Cursor QA
9.1. Gameplay mode
В gameplay mode должно быть:
Player movement = enabled
Camera control = enabled
Cursor = hidden
Cursor lock = locked
UI input = disabled / limited
9.2. Terminal mode
В terminal mode должно быть:
Player movement = disabled
Camera control = disabled
Cursor = visible
Cursor lock = unlocked
UI input = enabled
9.3. После закрытия UI
После закрытия терминала:
Player movement = enabled
Camera control = enabled
Cursor = hidden
Cursor lock = locked
9.4. Частые баги
Проверить:
cursor остаётся видимым после закрытия терминала;
камера двигается при открытом терминале;
игрок двигается при открытом терминале;
Esc не закрывает терминал;
Esc закрывает терминал, но не возвращает input;
после scene transition input не работает;
после save/load input не работает.

14. FPS Goals
14.1. First Playable rough goals
Для First Playable не нужен финальный FPS lock, но нужен ориентир.
Цель:
1080p LOW: playable on GTX 1050 Ti
Желательно:
60 FPS target on LOW
Допустимо на раннем First Playable:
45–60 FPS, если нет постоянных фризов
Плохо:
ниже 30 FPS
регулярные фризы
сильные просадки при UI
долгие зависания при смене сцен
14.2. Что считать проблемой
Проблема:
FPS падает ниже 30;
GPU frame time резко растёт на VFX;
UI вызывает просадки;
fog слишком дорогой;
dynamic lights слишком дорогие;
scene loading вызывает длинный freeze;
память растёт после каждого перехода.
15. Memory Baseline
15.1. Что проверять
Проверить:
RAM usage после старта;
RAM usage после перехода в Expedition 01;
RAM usage после возврата на станцию;
не растёт ли память после повторных переходов.
15.2. Красные флаги
Проблемы:
память растёт после каждого Station ↔ Expedition перехода
сцены не выгружаются
дублируются persistent objects
аудио/видео/текстуры остаются в памяти без причины
16. Build Size Baseline
16.1. Target
Желательный ориентир проекта:
финальный билд до 10 GB
Для First Playable билд должен быть намного меньше.
Ориентир для раннего First Playable:
до 2–4 GB
Если First Playable уже близок к 10 GB — это проблема.
16.2. Что проверять
Проверить:
размер билда;
какие папки/ассеты занимают больше всего;
нет ли случайных source files;
нет ли больших тестовых текстур;
нет ли лишнего контента из _Sandbox;
нет ли неиспользуемых аудио/видео.
17. Scene Loading Baseline
17.1. Что измерять
Измерить:
Station → Expedition 01
Expedition 01 → Station
Фиксировать:
load time
visible freeze
player spawn correctness

UI state after load
17.2. Цель
Для First Playable:
загрузка должна быть стабильной и без поломки состояния
Скорость важна, но не критична, если сцены маленькие.
18. Optimization Pass
18.1. Что можно оптимизировать в Sprint 08
Только простые вещи:
отключить лишние realtime shadows;
убрать лишние dynamic lights;
проверить fog intensity/cost;
проверить VFX particle count;
отключить тяжёлые debug objects;
убрать неиспользуемые объекты из сцен;
проверить texture import settings;
проверить audio compression;
проверить collider complexity;
проверить post-processing.
18.2. Что НЕ делать
Не делать:
глубокий render pipeline rewrite;
сложный addressables pipeline;
aggressive asset bundling;
shader rewrite;
LOD system для всего проекта;
occlusion culling pass;
сложную streaming system.
Это позже.
19. LOW Preset Assumptions
19.1. LOW должен предполагать
real-time shadows off or minimal
dynamic lights minimal
fog controlled
VFX reduced
post-processing reduced
texture quality reduced
baked lighting as base
19.2. Что проверить уже сейчас
Даже без полноценного меню настроек нужно проверить руками:
можно ли выключить realtime shadows;
не ломается ли читаемость без realtime shadows;
важные объекты видны без дорогих эффектов;
IO trace читается без heavy bloom;
Expedition 01 читается на упрощённом освещении.

26. Риски Sprint 08
26.1. Риск: начать фиксить всё подряд
Проблема:
QA найдёт много мелких проблем, и можно утонуть в minor fixes.
Решение:
Сначала Blocker.
Потом Critical.
Потом Major.
Minor — только если быстро.
26.2. Риск: начать преждевременную оптимизацию
Проблема:
Можно потратить много времени на глубокую оптимизацию без реальных замеров.
Решение:
Сначала baseline.
Потом простые очевидные правки.
Глубокую оптимизацию делать позже.
26.3. Риск: игнорировать билд
Проблема:
В Editor всё работает, а билд ломается.
Решение:
Sprint 08 считается готовым только после standalone build test.
26.4. Риск: переписать save
Проблема:
Save placeholder может потянуть полноценную save architecture.
Решение:
Сейчас нужен только First Playable state.
Без slots, autosave, cloud, profiles.
27. Главный результат Sprint 08
После Sprint 08 у проекта должен быть технический baseline First Playable:
мы знаем, что работает
мы знаем, что ломается
мы знаем, где просадки
мы знаем, что нужно исправить перед lock
Это переводит проект из состояния:
“кажется, работает”
в состояние:
“проверено, измерено, зафиксировано”
