NERA — Unity Project Structure
Назначение документа
Unity Project Structure описывает, как должны быть организованы файлы, папки, сцены, префабы, конфиги, UI, арт, VFX и аудио в Unity-проекте NERA.
Документ нужен, чтобы:
проект не превратился в хаос;
все игровые системы лежали в понятных местах;
контент станции и экспедиций был разделён;
общие ассеты не дублировались;
First Playable можно было собрать без мусора;
проект был готов к расширению до полной игры;
будущая работа с Addressables была возможна без полной перестройки.
01. Общий принцип структуры
Главная идея
Весь контент NERA должен лежать внутри одного корня проекта:
Assets/_Project/NERA/
Это позволяет отделить собственный контент игры от:
Unity packages;
Asset Store packages;
Plugins;
Third Party assets;
URP settings;
temporary imports;
test assets.
Почему нужен один корень
Один корень даёт:
чистый проект;
быстрый поиск файлов;
понятную структуру;
удобный перенос;
удобную чистку;
меньше случайного мусора;
меньше конфликтов с чужими ассетами.
Главный принцип
Всё, что относится к NERA, лежит в Assets/_Project/NERA/
Исключения допустимы только для:
Packages;
Plugins;
ThirdParty;
Asset Store assets;
Unity Render Pipeline settings;
external tools.

Главное правило
Если ассет используется в игре — он должен лежать в нормальной production-папке.
Если ассет экспериментальный — он лежит в:

_Sandbox/

кастомные окна и утилиты.

кастомные инспекторы.
Importers/
импорт и обработка ассетов, если понадобится.
Debug/
debug tools, validation tools.
Правило Runtime / Editor
Код из Editor не должен попадать в билд.
Код из Runtime не должен зависеть от UnityEditor.
Главное правило
Код должен быть разделён по системам, а не лежать в одной папке Scripts.
Нельзя делать:
Assets/Scripts/
Player.cs
Item.cs
Manager.cs
UI.cs
Test.cs
NewScript.cs

Если модель относится к станции — она идёт в Content/Station.
Если к древним — в Content/AncientNERA.
Если к планете — в Content/Planet.

25. Что не делать
Не хранить всё в одной папке
Плохо:
Assets/Models/
Assets/Materials/
Assets/Scripts/
Assets/Prefabs/
Это быстро станет хаосом.
Не смешивать тесты и production
Плохо:
Station_Terminal.prefab
Station_Terminal_TEST.prefab
Station_Terminal_old.prefab
Station_Terminal_final.prefab
Для тестов есть:
Tests/
_Development/
_Sandbox/
Не класть общие ассеты внутрь одной экспедиции
Плохо:
Expedition_01/Materials/M_Ancient_Stone
если этот материал потом используется в Expedition_02.
Лучше:
Content/AncientNERA/Materials/M_Ancient_Stone
Не плодить финальные версии
Плохо:
Expedition01_Final
Expedition01_Final2
Expedition01_New
Expedition01_RealFinal
Лучше использовать Git и нормальные имена.
Не делать папку Misc
Папка Misc почти всегда превращается в мусор.
Если хочется создать Misc, значит структура не продумана.

27. Главная мысль документа
Unity Project Structure нужна не для красоты папок, а для контроля разработки.
NERA будет расти через:
станцию;
экспедиции;
исследования;
переводы;
IO;
артефакты;
UI;
VFX;
аудио;
модульные ассеты.
Если структура будет плохой, проект начнёт тормозить не из-за Unity, а из-за хаоса.
Главное правило:
общий контент лежит в shared-папках;
уникальный контент лежит внутри своей локации;
код разделён по системам;
UI отделён от сцен;
тесты отделены от production;
временный мусор не попадает в игру.
