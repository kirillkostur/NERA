NERA — Production Bible
АКТУАЛЬНОЕ УТОЧНЕНИЕ: задачи Translation System, Translation UI и Translation Level исключены из production scope. Их место занимает связка Research → Library → progression unlock; см. «NERA — Current Scope Decisions», DD-001.
Назначение документа
Production Bible описывает порядок разработки NERA с учётом текущих реальных условий проекта.
Этот документ нужен не для описания лора, визуала или систем в теории. Его задача — превратить уже созданные Bible-документы в понятный план производства.
Документ отвечает на вопросы:
Что делать сначала?
Что входит в First Playable?
Какие системы нужны для первого рабочего билда?
Что можно отложить?
Как не раздуть проект?
Как двигаться маленькой командой?
Как собрать NERA в рабочую игру, а не в набор разрозненных сцен и идей?
01. Current Project Reality
Текущий статус
Проект NERA уже создан в Unity.
Текущее состояние:
Engine: Unity
Render Pipeline: URP
Камера: третье лицо уже реализована
Игровой цикл: ещё не реализован
Станция: ещё не реализована
Экспедиции: ещё не реализованы
Терминал: ещё не реализован
Инвентарь: ещё не реализован
Дрон: ещё не реализован
Исследования: ещё не реализованы
Библиотека / переводы: ещё не реализованы
Команда
Фактическая команда на старте:
ты — разработка, Unity, арт, свет, сборка сцен, техарт, дизайн;
я — помощь с документацией, структурой систем, логикой, планированием, задачами, ревью решений, текстами и дизайном.
Это означает, что производство должно быть максимально аккуратным по scope.
NERA нельзя планировать как игру для большой команды.
Нужно проектировать разработку так, чтобы один человек мог постепенно собрать рабочий результат.
Главная цель ближайшего этапа
Главная цель — First Playable для себя.
Это не публичное демо. Это не маркетинговый vertical slice. Это не финальная красивая версия.
First Playable нужен, чтобы проверить:
работает ли главный игровой цикл;
интересно ли возвращаться на станцию;
понятно ли, зачем идти в экспедицию;
работает ли связка находка → исследование → понимание;
есть ли ощущение NERA.
Ориентир по сроку
Ориентир на первый рабочий билд:
5–6 месяцев
Этот срок реалистичен только при условии:
использования готового или быстрого арта;
минимального количества систем;
минимального количества экспедиций;
отказа от раннего полиша;
отказа от лишних фич;
постоянного контроля объёма.
Главная мысль главы
NERA на старте должна разрабатываться как небольшой, управляемый First Playable, а не как вся полная игра сразу.
02. Production Vision
Главная идея
Разработка NERA должна идти от игрового цикла, а не от отдельных красивых фич.
Главный принцип:
Сначала рабочий loop.
Потом качество.
Потом масштаб.
Основной производственный loop
Минимальный рабочий loop NERA:
станция
↓
терминал
↓
дрон
↓
экспедиция
↓
находка
↓
возвращение на станцию
↓
исследование
↓
библиотека / перевод
↓
новое понимание
↓
новая цель
Именно этот loop должен быть собран первым.
Что нельзя делать на старте
На старте нельзя уходить в:
10 экспедиций;
финальную локацию;
сложную систему языка;
много типов IO;
полный UI;
полный набор апгрейдов;
много предметов;
много арта станции;
идеальную оптимизацию;
финальные материалы;
полный саунд-дизайн;
полный сюжет.
На старте нужна не полнота, а связность.
Главная мысль главы
Если игрок может пройти один полный цикл NERA, проект живой. Если есть красивые куски без цикла — проект пока не работает.
03. Development Principles
Принцип 1. First Playable First
Главная цель первых 5–6 месяцев — не демо для игроков, а рабочая версия для себя.
Она должна позволить честно ответить:
играется ли это;
понятен ли loop;
интересно ли исследовать;
работает ли станция как hub;
работает ли экспедиция как вылазка;
даёт ли исследование ощущение прогресса.
Принцип 2. One Complete Example
Для каждой крупной системы сначала делается один полный пример.
Примеры:
одна рабочая экспедиция;
одна древняя запись;
один исследуемый объект;
один результат исследования;
один частичный перевод;
одна запись в библиотеке;
один запуск дрона;
одна точка на карте;
один IO;
одна ? точка, если успеваем.
Пока один пример не работает, нельзя масштабировать систему.
Принцип 3. Greybox Before Art
Все локации сначала делаются как blockout / greybox.
Проверяется:
маршрут;
вход;
выход;
альтернативный путь;
боковая комната;
место находки;
место IO;
возврат;
shortcut;
читаемость пространства.
Арт приходит только после того, как локация работает.
Принцип 4. System Before Content
Сначала система, потом контент.
Правильный порядок:
сначала инвентарь → потом много предметов;
сначала Research System → потом много объектов;
сначала Library UI → потом много записей;
сначала Drone flow → потом много экспедиций;
сначала один IO → потом вариации;
сначала карта → потом много точек.
Принцип 5. No Feature Without Function
Любая фича должна отвечать на вопрос:
Как она усиливает исследование, любопытство или понимание мира?
Если ответ слабый — фича не нужна в First Playable.
Принцип 6. Production-Friendly Design
Все решения должны быть посильны маленькой команде.
Предпочтение отдаётся:
модульным ассетам;
простым системам;
переиспользованию;
минимальному UI;
простым VFX;
baked lighting;
контролируемым dynamic lights;
коротким, но завершённым локациям.
Главная мысль главы
NERA должна строиться не шириной, а глубиной одного рабочего примера.
04. First Playable Definition
Назначение главы
Эта глава определяет, что считается первым рабочим билдом NERA.
Что такое First Playable
First Playable — это внутренняя версия игры, где уже можно пройти основной цикл.
Она не обязана быть красивой. Она не обязана быть оптимальной. Она не обязана быть понятной внешнему игроку без объяснения.
Но она должна быть играбельной от начала до конца выбранного куска.
Минимальная структура First Playable
First Playable должен включать:
старт на станции;
частично сломанную станцию;
простое восстановление питания;
рабочий терминал;
простую карту;
запуск дрона;
открытие первой экспедиции;
переход в экспедицию;
одну экспедиционную локацию;
одну древнюю запись;
один исследуемый объект;
одну встречу с IO или след IO;
возврат на станцию;
исследование объекта;
обновление библиотеки;
частичный перевод записи;
понятный намёк на следующий шаг.
First Playable не должен включать
10 экспедиций;
полный сюжет;
финальный выбор;
все типы IO;
все апгрейды станции;
полную систему антенны;
много ? точек;
полный звук;
финальный UI;
полный арт всех комнат;
полную оптимизацию;
финальные настройки графики.
Главная проверка First Playable
После прохождения First Playable нужно ответить:
Хочется ли сделать следующую экспедицию?
Понятно ли, зачем нужна станция?
Понятно ли, зачем нужны находки?
Работает ли ощущение исследования?
Есть ли эмоция “я понял немного больше”?
Не слишком ли нудный loop?
Главная мысль главы
First Playable должен доказать, что NERA работает как игра, а не только как концепт.
05. First Playable Content Scope
Назначение главы
Эта глава фиксирует объём контента для первого рабочего билда.
Станция
Для First Playable достаточно минимальной станции.
Нужны:
стартовая точка игрока;
терминал;
солнечная панель или источник питания;
батарея / energy state;
лабораторный стол;
хранилище или простой storage;
выход в экспедицию;
место для дрона;
1–2 декоративные комнаты или зоны.
Не нужно сразу делать все 5–8 комнат станции в финальном виде.
Экспедиция
Нужна одна экспедиция.
Функционально это:
Expedition 01 — первая локация цивилизации NERA
Она должна показать:
древняя цивилизация существовала;
здесь кто-то жил;
есть древняя запись;
есть объект для исследования;
язык пока непонятен;
после исследования появляется новое понимание.
IO
Для First Playable достаточно:
один Blue IO
или даже:
след присутствия IO без полноценного боя
Но лучше иметь хотя бы один простой рабочий IO, чтобы проверить угрозу.
Дрон
Для First Playable дрон может быть максимально простым.
Нужно:
кнопка Launch;
статус In Flight;
таймер или быстрый возврат;
после возврата карта получает экспедицию;
дрон уходит на зарядку.
Не нужно:
анимация полноценного полёта;
сложная зона сканирования;
много результатов;
улучшения дрона;
ручное управление.
Исследование
Для First Playable достаточно одного исследования.
Пример:
Unknown Ancient Object
↓
Analysis
↓
Research Result
↓
Library Entry Updated
↓
Translation Level changed from Unknown to Fragmented / Partial
Библиотека
Нужна простая библиотека:
список записей;
карточка выбранной записи;
статус перевода;
исходный текст;
частичный перевод;
обновление после исследования.
Инвентарь
Нужен простой инвентарь:
3 quick slots;
5 backpack slots;
item pickup;
item details;
drop optional;
use optional;
send to research.
Аномальные слоты можно отложить, если они мешают First Playable.
Главная мысль главы
First Playable должен быть маленьким, но полным.
Лучше одна законченная экспедиция со станционным loop, чем три недоделанные карты.
06. Development Stages
Назначение главы
Эта глава описывает порядок разработки до First Playable.
Stage 01 — Project Foundation
Цель
Подготовить основу Unity-проекта для дальнейшей разработки.
Уже готово
Unity project создан;
URP настроен;
камера от третьего лица есть.
Нужно сделать
проверить структуру папок проекта;
настроить базовые сцены;
создать сцену станции;
создать сцену первой экспедиции;
создать базовый Game Manager / Scene Flow;
создать базовую систему загрузки между сценами;
завести правила именования;
создать папки для configs, prefabs, UI, scenes, art, audio.
Результат Stage 01
проект готов к сборке игровых систем;
есть пустая станция;
есть пустая экспедиция;
игрок может быть размещён в сцене;
есть базовый переход между сценами или подготовка к нему.
Stage 02 — Player and Interaction Foundation
Цель
Сделать базовое взаимодействие игрока с миром.
Нужно сделать
проверить third-person controller;
настроить movement feel;
добавить Interaction System;
добавить interact prompt;
добавить pickup item;
добавить простые interactable объекты;
добавить long interaction для ремонта / чистки;
добавить базовые предметы.
Минимальные проверки
Игрок должен:
подойти к объекту;
увидеть подсказку;
подобрать предмет;
активировать объект;
удерживать кнопку для долгого действия.
Результат Stage 02
игрок может физически взаимодействовать с миром.
Stage 03 — Station Core
Цель
Сделать станцию рабочим hub.
Нужно сделать
сцена станции;
простая broken state логика;
солнечная панель / источник питания;
clean / repair interaction;
battery / energy state;
включение терминала;
выход к экспедиции;
простые station states.
Минимальный сценарий
игрок появляется на станции;
терминал не работает;
игрок чистит / чинит источник питания;
энергия появляется;
терминал включается.
Результат Stage 03
станция начинает ощущаться как рабочий объект, который игрок оживляет.
Stage 04 — Terminal and Map
Цель
Сделать базовый терминал и карту.
Нужно сделать
открытие полноэкранного UI терминала;
главный экран терминала;
простая карта;
карточка точки;
статус locked / available / completed;
кнопка запуска дрона или перехода в Drone tab;
кнопка перехода в экспедицию после открытия.
Минимальный UI
Достаточно простых экранов:
Terminal Home;
Map;
Drone;
Research;
Library.
Не нужно финальное оформление.
Результат Stage 04
игрок может открыть терминал и понять, что дальше делать.
Stage 05 — Drone Flow
Цель
Сделать дрон как инструмент открытия экспедиций.
Нужно сделать
Drone UI;
Launch Drone;
статус In Flight;
таймер;
Drone Returned;
добавление Expedition 01 на карту;
статус Charging / Ready.
Минимальный сценарий
игрок запускает дрон;
дрон “летит”;
после возвращения появляется новая точка экспедиции;
игрок может выбрать её на карте.
Что можно не делать
3D-анимацию дрона;
ручное управление;
сложный радиус сканирования;
много вариантов результата;
улучшения дрона.
Результат Stage 05
игрок понимает: дрон открывает новые экспедиции.
Stage 06 — Expedition 01 Greybox
Цель
Собрать первую экспедицию как играбельную локацию.
Нужно сделать
blockout локации;
вход;
основной маршрут;
1 альтернативный путь или боковая комната;
место древней записи;
место исследуемого объекта;
место IO или следа IO;
возврат к выходу;
shortcut назад, если успеваем.
Функция Expedition 01
Expedition 01 должна отвечать на вопрос:
Кто жил на NERA?
Она должна дать эмоцию:
Здесь кто-то жил.
Результат Stage 06
первую экспедицию можно пройти от входа до выхода.
Stage 07 — Inventory and Items
Цель
Сделать базовый item loop.
Нужно сделать
3 quick slots;
5 backpack slots;
pickup item;
item data;
item description;
item type;
inventory screen;
выбор предмета;
предмет для исследования;
древняя запись как collectible / readable data.
Что можно отложить
10 / 15 слотов рюкзака;
аномальные слоты;
сложную сортировку;
storage;
drop system;
много категорий предметов.
Результат Stage 07
игрок может найти и принести предмет на станцию.
Stage 08 — Research and Library
Цель
Сделать цикл находка → исследование → знание.
Нужно сделать
Research UI;
список доступных объектов;
Start Analysis;
таймер или мгновенный анализ для прототипа;
Research Complete;
результат исследования;
Library Entry;
обновление записи;
Translation Level.
Минимальный сценарий
игрок приносит ancient object;
запускает анализ;
получает результат;
в библиотеке появляется запись;
древний текст становится понятнее.
Результат Stage 08
игрок получает ощущение, что экспедиция дала знание.
Stage 09 — Basic IO
Цель
Сделать один рабочий тип IO.
Нужно сделать
Blue IO;
простое поведение;
обнаружение игрока;
движение к игроку или patrol;
простая атака / зона опасности;
получение урона или способ избежать;
VFX mesh + glow;
базовый звук, если есть;
кристалл после смерти, если нужно.
Важно
IO не должен сразу быть сложным врагом.
Для First Playable достаточно проверить:
игрок воспринимает IO как угрозу;
IO читается визуально;
встреча не ломает темп экспедиции;
после IO остаётся смысловая находка или след.
Результат Stage 09
в игре появляется первая опасность.
Stage 10 — First Playable Assembly
Цель
Собрать весь loop в одну последовательность.
Игровая последовательность
1. Игрок появляется на станции.
2. Терминал выключен.
3. Игрок восстанавливает питание.
4. Терминал включается.
5. Игрок запускает дрон.
6. Дрон открывает Expedition 01.
7. Игрок отправляется в Expedition 01.
8. Игрок находит древнюю запись.
9. Игрок находит объект для исследования.
10. Игрок встречает IO или след IO.
11. Игрок возвращается на станцию.
12. Игрок исследует объект.
13. Библиотека обновляется.
14. Перевод записи улучшается.
15. Игрок получает намёк на следующую экспедицию.
Результат Stage 10
NERA становится First Playable.
07. 5–6 Month Production Roadmap
Назначение главы
Эта глава описывает примерное распределение работ на 5–6 месяцев.
Это не жёсткий календарь, а ориентир.
Month 1 — Foundation
Цель
Подготовить проект и базовые взаимодействия.
Фокус
структура проекта;
сцена станции;
сцена Expedition 01;
переходы между сценами;
interaction system;
pickup;
long interaction;
первый blockout станции.
Результат месяца
игрок ходит по станции;
может взаимодействовать с объектами;
может подбирать предмет;
есть основа сцен.
Month 2 — Station and Terminal
Цель
Сделать станцию как рабочий hub.
Фокус
broken station state;
clean / repair solar panel;
basic energy state;
terminal activation;
terminal UI;
map UI;
drone UI placeholder.
Результат месяца
игрок может включить станцию и открыть терминал.
Month 3 — Drone and Expedition 01
Цель
Сделать переход к первой экспедиции.
Фокус
drone launch flow;
map point unlock;
Expedition 01 greybox;
scene transition;
entry / exit logic;
basic expedition objective;
ancient record placement;
research object placement.
Результат месяца
игрок может открыть первую экспедицию и пройти её в greybox.
Month 4 — Inventory, Research, Library
Цель
Собрать loop знания.
Фокус
inventory screen;
item data;
research UI;
analysis flow;
library UI;
ancient record;
translation levels;

15. Risk List
Назначение главы
Эта глава фиксирует основные риски разработки.
Risk 1 — Scope Creep
Самый большой риск NERA — расползание объёма.
Опасные признаки:
добавляется новая система до завершения старой;
появляется новая экспедиция до готовности первой;
делается финальный арт до рабочего loop;
усложняется язык;
усложняется UI;
добавляется много предметов;
хочется сразу сделать “как в полной игре”.
Risk 2 — UI Overload
NERA сильно зависит от терминала, карты, библиотеки и перевода.
Есть риск сделать слишком много окон и текста.
Решение:
сначала минимальный UI;
одна запись;
один перевод;
одна карточка;
один результат исследования.
Risk 3 — Boring Loop
Главный вопрос First Playable:
не нудно ли это?
Если игроку скучно возвращаться на станцию и исследовать находки, нужно менять темп.
Проверять:
длина экспедиции;
количество действий на станции;
скорость исследования;
количество текста;
ясность награды;
интерес следующего шага.
Risk 4 — Art Before Gameplay
Есть риск слишком рано уйти в красивую станцию или красивые руины.
Решение:
greybox first;
lighting pass после gameplay;
art pass только на нужные зоны;
не делать невидимый игроку контент.
Risk 5 — Performance
Даже stylized игра может стать тяжёлой из-за:
много realtime lights;
много transparent VFX;
много fog;
тяжёлые материалы;
плохой culling;
нет LOD;
много уникальных текстур.
Решение:
baked lighting;
ограниченные dynamic lights;
ранний LOW-профиль;
простые материалы;
модульность;
контроль VFX.
Risk 6 — Working Alone
Так как фактически разработка идёт одним человеком, опасно делать слишком много параллельных направлений.
Решение:
одна главная задача за раз;
короткие milestones;
каждую неделю проверять loop;
не открывать 10 фронтов одновременно;
вести список отложенных идей.
16. Scope Control Rules
Назначение главы
Эта глава фиксирует правила контроля объёма.
Правило 1. Если не нужно для First Playable — в backlog
Любая идея, которая не нужна для первого loop, уходит в backlog.
Правило 2. Один пример перед масштабом
Нельзя делать 10 объектов, пока не работает один.
Правило 3. Нет новой системы без удаления или заморозки другой
Если добавляется новая система, нужно проверить, не перегружает ли она производство.
Правило 4. Каждая задача должна иметь результат в игре
Плохая задача:
подумать над системой языка
Хорошая задача:
сделать одну древнюю запись с состояниями Unknown / Fragmented / Partial
Правило 5. Любой polish после gameplay
Если механика не работает, polish откладывается.
Главная мысль главы
Scope control — это не ограничение творчества, а защита проекта от незавершённости.

18. First Playable Acceptance Criteria
Назначение главы
Эта глава фиксирует критерии готовности First Playable.
First Playable считается готовым, если:
игрок стартует на станции;
станция частично не работает;
игрок восстанавливает питание;
терминал включается;
игрок запускает дрон;
дрон открывает первую экспедицию;
игрок переходит в экспедицию;
экспедиция имеет вход, маршрут, находку и выход;
игрок находит древнюю запись;
игрок находит объект для исследования;
игрок встречает IO или след IO;
игрок возвращается на станцию;
игрок запускает исследование;
исследование завершается;
библиотека обновляется;
перевод становится понятнее;
игрок понимает, что следующим шагом будет новая экспедиция.
Дополнительные критерии
Желательно:
есть базовый звук;
есть базовый свет;
есть базовый fog;
есть минимальный art pass;
есть сохранение;
есть хотя бы LOW-настройки или понимание, что отключается на LOW;
нет критических багов прохождения.
Главный критерий
После прохождения First Playable должен появиться вопрос:
Что дальше?
Если игрок после этого не хочет идти в следующую экспедицию, loop нужно переделывать.
19. After First Playable
Назначение главы
Эта глава описывает, что делать после готовности First Playable.
Следующий этап
После First Playable нужно не сразу делать всю игру.
Нужно провести ревью.
Вопросы ревью
Работает ли станция как hub?
Интересно ли возвращаться?
Не слишком ли длинная экспедиция?
Не слишком ли много UI?
Не слишком ли мало награды?
Хочется ли исследовать предметы?
Работает ли перевод?
Понятно ли, что делать дальше?
IO мешает или усиливает игру?
Свет и атмосфера уже дают ощущение NERA?
Возможные решения после ревью
ускорить исследования;
сократить станционные действия;
сделать экспедицию короче;
усилить находки;
улучшить карту;
упростить UI;
добавить вторую экспедицию;
добавить первую ? точку;
добавить Anomaly Slots;
добавить Station Upgrade;
улучшить IO.
Следующий milestone
После First Playable логично делать:
Vertical Slice
Но уже не для себя, а потенциально для показа.
Vertical Slice должен быть красивее, плотнее и понятнее внешнему игроку.
