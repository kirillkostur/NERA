NERA — Sprint 09 Plan
First Playable Lock
1. Назначение Sprint 09
Sprint 09 нужен, чтобы зафиксировать First Playable как стабильный milestone.
После Sprint 08 у нас уже должны быть:
full flow QA
bug list
performance baseline
memory baseline
build size baseline
loading baseline
must-fix list
standalone build test
Sprint 09 не должен расширять игру.
Его задача:
закрыть blockers
→ закрыть critical bugs
→ убрать лишний debug из основного flow
→ зафиксировать состав First Playable
→ собрать milestone build
→ оформить release notes
2. Главная цель спринта
Цель
Сделать версию First Playable, которую можно считать стабильной внутренней сборкой.
После Sprint 09 должно быть понятно:
что входит в First Playable;
что не входит в First Playable;
какие баги исправлены;
какие баги остаются известными;
какой build является milestone;
можно ли пройти игру от начала до конца;
какие следующие шаги после lock.
Главный результат:
NERA First Playable locked as internal milestone
3. Почему это важно
Без lock проект может застрять в бесконечном состоянии:
ещё чуть-чуть улучшим
ещё один эффект
ещё один UI экран
ещё один фикс
ещё одна маленькая система
Это опасно.
First Playable нужен не для идеала.
First Playable нужен, чтобы доказать:
core loop NERA работает
4. Главный принцип Sprint 09
Sprint 09 — это спринт фиксации.
Правило:
Если задача не нужна для стабильного прохождения First Playable — она не входит в Sprint 09.
5. First Playable Lock Definition
5.1. Что значит “First Playable locked”
First Playable считается locked, если:
полный loop проходится от начала до конца;
нет blocker bugs;
critical bugs закрыты или явно приняты как known issues;
билд собирается;
билд запускается;
standalone build проходится без debug;
состав контента зафиксирован;
дальнейшие изменения идут уже после milestone.
5.2. Что НЕ значит “locked”
Locked не значит:
финальное качество;
готовность к публичному показу;
vertical slice;
demo для Steam;
trailer-ready build;
art complete;
audio complete;
optimization complete;
production complete.
Это только:
внутренний стабильный First Playable

7. Required Full Flow
7.1. Обязательный проход
Milestone build должен проходиться так:
Start on Station
→ Restore Station Power
→ Open Terminal
→ Launch Drone
→ Discover Expedition 01
→ Travel to Expedition 01
→ Explore Ancient Outpost
→ Read Ancient Record
→ Inspect NERA Memory Core
→ Notice IO Trace
→ Return to Station
→ Analyze NERA Memory Core
→ Library Updated
→ Ancient Language Level: Fragmented
→ Next Objective Hint
7.2. Запрещено для lock
В milestone build нельзя, чтобы обязательный проход зависел от:
debug unlock
manual inspector changes
editor-only objects
scene reload by hand
console commands
temporary keyboard shortcuts that are not documented
Debug-инструменты можно оставить, но они не должны быть частью прохождения.
8. Bug Fix Priority
8.1. Blocker bugs
Все blocker bugs должны быть закрыты.
Blocker examples:
build does not launch
station scene does not load
expedition scene does not load
player cannot move
terminal cannot open
drone scan cannot complete
travel button does not work
return to station does not work
research cannot complete
game crashes
Правило:
Blocker нельзя переносить после First Playable Lock.
8.2. Critical bugs
Critical bugs должны быть:
исправлены;
или явно записаны как accepted known issue, если они не ломают milestone.
Critical examples:
cursor remains visible after terminal
input sometimes breaks after scene transition
objective hint does not update
UI displays wrong state after load
collected objects appear again
save/load restores incomplete state
8.3. Major bugs
Major bugs можно перенести после lock, если:
они не ломают прохождение;
не мешают понять loop;
не портят базовый опыт слишком сильно.
8.4. Minor bugs
Minor bugs не должны задерживать lock.
Примеры:
typos
rough alignment
placeholder icons
minor clipping
temporary materials
weak audio mix
9. Debug Cleanup
9.1. Что оставить
Можно оставить debug-инструменты:
Debug_Save
Debug_Load
Debug_Reset
Debug_UnlockExpedition01
Debug_GiveResearchObject01
Debug_SetTranslationFragmented
Но они должны быть:
явно подписаны;
не видны обычному игроку;
не обязательны для прохождения;
не мешать UI.
9.2. Что убрать
Убрать из обычного flow:
debug buttons inside main terminal panels
temporary cheat prompts
editor-only instructions
visible debug state text
test cubes without purpose
obsolete placeholder triggers
duplicated scene transition objects
9.3. Debug naming
Все оставленные debug-инструменты должны быть в одном месте:
Debug
UI_Debug
DebugSessionControls
10. Build Naming
10.1. Milestone build name
Формат:
NERA_FP_LOCK_v0.1.0_YYYY_MM_DD
Пример:
NERA_FP_LOCK_v0.1.0_2026_07_31
10.2. Почему v0.1.0
v0.1.0 означает:
первый зафиксированный внутренний First Playable
Это не публичная версия.
11. Version Rules
11.1. Version format
Использовать формат:
Major.Minor.Patch
Для внутренней разработки:
0.1.0 = First Playable Lock
0.1.1 = Hotfix after First Playable Lock
0.2.0 = Next major internal milestone
11.2. Что считается patch
Patch повышается, если:
исправили баг;
не добавили новую систему;
не расширили scope;
не изменили milestone content.
Пример:
0.1.0 → 0.1.1
11.3. Что считается minor
Minor повышается, если:
добавили новый крупный кусок loop;
добавили новую экспедицию;
добавили антенну;
добавили ? точки;
добавили полноценный inventory UI.
Пример:
0.1.0 → 0.2.0

20. Риски Sprint 09
20.1. Риск: добавить “маленькую” новую фичу
Проблема:
маленькая фича может сломать стабильный flow
Решение:
В Sprint 09 новые фичи запрещены.
Только fix / cleanup / lock.
20.2. Риск: бесконечно фиксить minor bugs
Проблема:
Можно не залочить milestone из-за мелочей.
Решение:
Minor bugs идут в known issues.
Lock не должен зависеть от них.
20.3. Риск: потерять стабильный build
Проблема:
После успешного build можно продолжить менять проект и потерять рабочее состояние.
Решение:
Milestone build архивируется.
Версия фиксируется.
Дальнейшие изменения идут после lock.
20.4. Риск: считать FP готовым к публичному показу
Проблема:
First Playable может ошибочно восприниматься как vertical slice.
Решение:
В release notes явно указать:
это internal First Playable, не public demo.
21. Главный результат Sprint 09

NERA First Playable v0.1.0

core loop доказан
проект можно пройти
системы связаны
состояние фиксируется
дальше можно осознанно планировать следующий этап
22. Следующий шаг
После Sprint 09 логично сделать не новый спринт сразу, а отдельный документ:
Post-First Playable Review
Он должен ответить:
что в First Playable получилось;
что не получилось;
какие системы надо переписать;
что можно оставить;
что выкинуть;
какой следующий milestone;
делать ли Expedition 02;
когда добавлять антенну;
когда добавлять ? точки;
нужно ли усиливать IO;
когда начинать full inventory;
когда делать real map;
что будет следующим главным production-слоем.
После First Playable Lock проект должен перейти из режима:
собираем первый рабочий loop
в режим:
решаем, какой следующий слой делает NERA сильнее
