# NERA Quest Editor — полное руководство

Updated: 2026-08-01

## 1. Назначение

Эта документация описывает:

- окно `NERA Quests` для создания и поиска квестов;
- Inspector ассета `QuestDefinition`;
- все поля условий и этапов;
- автоматическую регистрацию квестов в каталоге;
- настройку одноразовых и повторяемых заданий;
- игровые события, уже подключённые к квестовой системе;
- правила сохранения, валидации и диагностики.

Квесты настраиваются в ScriptableObject-конфигах. Для обычного добавления
контента изменять `QuestController` или другой runtime-код не требуется.

## 2. Модель квеста

У квеста есть две независимые настройки: повторяемость и способ выбора цели.

### 2.1. Повторяемость

| Значение | Поведение |
|---|---|
| `Появляется один раз` | После завершения квест записывается в историю сохранения и больше не активируется. |
| `Может появляться снова` | После завершения квест может снова активироваться, когда повторно выполнятся условия появления. |

Это единственные два вида жизненного цикла. `Основное` и `Второстепенное` —
только разделы будущего журнала, а не дополнительный тип поведения.

### 2.2. Цель квеста

| Значение | Когда использовать | ID runtime-экземпляра |
|---|---|---|
| `Один общий квест` | Сюжетная цепочка, одна глобальная атака, общее задание станции. | `questId` |
| `Отдельный квест для вызвавшего объекта` | Панели, турели, генераторы и другие объекты, которым нужен независимый квест. | `questId:targetId` |

Объектный квест запоминает `targetId` и `targetName` события, которое вызвало
его появление. Пока экземпляр активен, повторные события того же объекта не
создают дубликат.

Для одноразового объектного квеста правило «один раз» применяется отдельно к
каждому `targetId`. Для повторяемого объектного квеста один и тот же объект
может создать новый экземпляр после завершения предыдущего.

## 3. Окно `NERA Quests`

### 3.1. Как открыть

В главном меню Unity выберите:

`NERA -> Quests -> Open Quest Editor`

Откроется окно с заголовком `NERA Quests`.

### 3.2. Кнопка `Создать одноразовый квест`

Кнопка создаёт новый ассет в:

`Assets/_Project/NERA/Configs/Quests`

Имя файла создаётся в форме `Quest_OneTime.asset`. Если файл уже существует,
Unity автоматически добавит уникальный суффикс.

Начальные значения:

| Поле | Значение |
|---|---|
| Повторяемость | `Появляется один раз` |
| Раздел журнала | `Основное задание` |
| Цель квеста | `Один общий квест` |
| Quest ID | `main.new_one_time_XXXXXXXX` |
| Название | `Новый квест` |
| Условие появления | `Локация обнаружена`, конкретный ID пока пуст |
| Первый этап | `Новый этап`, конкретный ID пока пуст |

`XXXXXXXX` — случайный уникальный фрагмент. Его можно заменить осмысленным ID
до начала использования квеста в сохранениях.

После создания ассет автоматически добавляется в каталог, выделяется в окне
Project и открывается в Inspector.

### 3.3. Кнопка `Создать повторяемый квест`

Кнопка создаёт `Quest_Repeatable.asset` с уникальным именем и следующими
начальными значениями:

| Поле | Значение |
|---|---|
| Повторяемость | `Может появляться снова` |
| Раздел журнала | `Второстепенное задание` |
| Цель квеста | `Отдельный квест для вызвавшего объекта` |
| Quest ID | `side.new_repeatable_XXXXXXXX` |
| Название | `Новый квест` |
| Условие появления | `Локация обнаружена`, любой объект |
| Первый этап | событие от объекта, вызвавшего квест |

Тип игрового события создаётся как безопасная заготовка. Его необходимо
заменить на реальное событие: загрязнение панели, неисправность турели,
обнаружение врага и так далее.

### 3.4. Поиск

Поле `Поиск` фильтрует список одновременно по:

- отображаемому названию квеста;
- `Quest ID`.

Поиск не зависит от регистра. Он не меняет ассеты и не влияет на каталог.

### 3.5. Группы `Одноразовые` и `Повторяемые`

Все найденные `QuestDefinition` автоматически распределяются по двум группам.
В строке показаны название и `Quest ID`.

Кнопка `Открыть`:

- выделяет конфиг в Project;
- показывает его в Inspector;
- подсвечивает файл в Project Browser.

### 3.6. Кнопка `Обновить список`

Повторно сканирует проект и обновляет содержимое окна. Обычно список
обновляется автоматически через `EditorApplication.projectChanged`.

Кнопка полезна, если ассет был создан, перемещён или переименован внешним
инструментом, а окно ещё не отобразило изменение.

### 3.7. Кнопка `Синхронизировать каталог`

Собирает все `QuestDefinition` проекта, сортирует их по `Quest ID` и записывает
в:

`Assets/_Project/NERA/Resources/Quests/QuestCatalog_Default.asset`

Ручное добавление ссылок в каталог не требуется.

Синхронизация также выполняется автоматически:

- после создания, удаления или перемещения `.asset` в `Configs/Quests`;
- при загрузке editor-кода;
- непосредственно перед сборкой игры.

Если найдены одинаковые `Quest ID`, Unity выводит ошибку. Перед build такая
ошибка блокирует сборку.

Дополнительный пункт меню выполняет ту же операцию:

`NERA -> Quests -> Sync Quest Catalog`

## 4. Inspector `QuestDefinition`

Inspector открывается после создания квеста или выбора его ассета в Project.
Настройки расположены в порядке, в котором квест работает в игре.

## 5. Раздел `1. Поведение`

### 5.1. `Повторяемость`

`Появляется один раз`:

- после завершения создаётся запись в истории;
- повторный сигнал появления игнорируется;
- состояние сохраняется в `SaveGameData`.

`Может появляться снова`:

- активный экземпляр всё равно не дублируется;
- после завершения новый экземпляр разрешён;
- повторное появление произойдёт только после нового подходящего игрового
  события;
- квест обязан иметь хотя бы одно условие появления.

### 5.2. `Раздел журнала`

| Значение | Назначение |
|---|---|
| `Основное задание` | Сюжетные и обязательные цепочки. |
| `Второстепенное задание` | Обслуживание, аварии, нападения и дополнительные задачи. |

Раздел не влияет на активацию или завершение. Он предназначен для группировки
в будущем HUD/терминале.

### 5.3. `Цель квеста`

`Один общий квест` не запоминает объект события как контекст. Такой квест
удобен, когда все ID можно указать явно или когда подходит любой объект.

`Отдельный квест для вызвавшего объекта` запоминает объект первого подходящего
события. После этого в условиях этапов становится доступен вариант
`Объект, вызвавший этот квест`.

Объектный режим требует хотя бы одно условие появления: без события системе
неоткуда получить `targetId`.

### 5.4. Рекомендуемые сочетания

| Сценарий | Повторяемость | Цель |
|---|---|---|
| Сюжетная экспедиция | Один раз | Один общий квест |
| Одноразовое знакомство с конкретным устройством | Один раз | Для вызвавшего объекта |
| Глобальная волна нападения | Повторяемый | Один общий квест |
| Загрязнение каждой солнечной панели | Повторяемый | Для вызвавшего объекта |
| Неисправность каждой турели | Повторяемый | Для вызвавшего объекта |

## 6. Раздел `2. Название и отображение`

### 6.1. `Quest ID`

Уникальный стабильный ID квеста. Примеры:

- `main.expedition_01`;
- `side.clean_solar_panel`;
- `side.restore_turret`.

Правила:

- использовать латиницу, цифры, точки и `_`;
- не использовать отображаемое название как ID;
- не создавать два конфига с одинаковым ID;
- не менять ID после того, как квест попал в сохранения игроков.

Inspector автоматически обрезает пробелы и приводит ID к нижнему регистру.
История и активные экземпляры в сохранении связаны именно с этим значением.

### 6.2. `Название`

Короткое имя квеста для журнала и уведомлений.

Для объектного квеста можно использовать `{targetName}`:

`Очистите {targetName}`

При активации будет подставлено отображаемое имя объекта, полученное вместе с
игровым событием. Если имя не передано, используется `targetId`.

### 6.3. `Описание`

Развёрнутое описание общего задания. Также поддерживает `{targetName}`.

Не путать с описанием этапа: здесь описывается весь квест, а в этапе — текущая
задача игроку.

### 6.4. `Приоритет`

Чем больше число, тем выше квест в отсортированном списке активных заданий.
`TrackedQuest` выбирается из этого списка. При одинаковом приоритете задания
сортируются по ID экземпляра.

Текущие примеры:

- сюжетная экспедиция: `100`;
- восстановление турели: `40`;
- очистка панели: `30`.

### 6.5. `Показывать в HUD`

Определяет, может ли активный квест попасть в компактный HUD-блок
`HUD_Canvas/Quest_System`.

HUD содержит два слота:

- `Text - QuestMain` показывает основное задание с наивысшим приоритетом;
- `Text - QuestSide` показывает второстепенное задание с наивысшим приоритетом.

Каждый слот выводит тип задания, название квеста и текущую цель этапа. Когда
задание завершается, HUD сразу выбирает следующее активное задание той же
категории. Если подходящих заданий нет, соответствующий текст очищается. Если
не осталось ни основного, ни второстепенного задания, фон `Quest_System`
скрывается.

Квест с выключенным `Показывать в HUD` продолжает нормально активироваться,
продвигаться и сохраняться, но не участвует в выборе HUD-слота.

Отдельный полный журнал всех заданий в терминале пока не реализован.

## 7. Раздел `3. Когда появляется квест`

Здесь задаются условия активации.

Если условий несколько, появляется поле `Как объединять`:

- `Нужно выполнить все условия` — логика AND;
- `Достаточно любого условия` — логика OR.

По умолчанию используется AND, поэтому существующие квесты продолжают работать
как раньше.

Для общего квеста разные условия могут выполняться событиями разных объектов.
Для объектного квеста незавершённый прогресс хранится отдельно по `targetId`,
поэтому все условия появления должны выполняться для одного и того же объекта.

Если удалить все условия:

- одноразовый общий квест активируется автоматически при запуске игровой
  сессии;
- повторяемый квест считается некорректным;
- объектный квест считается некорректным.

Кнопки условия:

| Элемент | Действие |
|---|---|
| `↑` | Поднять условие выше. |
| `↓` | Опустить условие ниже. |
| `×` | Удалить условие. |
| `+ Добавить условие` | Создать новое условие. |

Порядок условий не меняет выбранную логику, но влияет на порядок отображения и
на позиции прогресса в сохранении.

## 8. Раздел `4. Этапы квеста`

Этапы выполняются строго сверху вниз. Следующий этап начинает принимать
события только после завершения текущего.

### 8.1. Поля этапа

`Задача игроку` — короткая текущая цель, например:

`Отправляйтесь в Ancient Outpost`

`Подробности` — дополнительное объяснение текущего этапа.

Оба поля поддерживают `{targetName}` в объектном квесте.

`Чекпоинт после завершения` — после выполнения именно этого этапа сохраняет
полный rollback snapshot и текущую позицию игрока. После смерти игрок вернётся
к этой точке, пока не будет создан более новый чекпоинт. Флаг подходит для
важной награды, необратимого изменения мира или длинного квеста, который не
должен целиком повторяться после смерти.

`Условия завершения этапа` — одно или несколько игровых условий. Для двух и
более условий появляется такое же поле `Как объединять`: выполнить все или
любое условие.

### 8.2. Кнопки этапа

| Элемент | Действие |
|---|---|
| `↑` | Переместить этап раньше. |
| `↓` | Переместить этап позже. |
| `Удалить` | Удалить этап со всеми условиями. |
| `+ Добавить этап` | Добавить этап с одним начальным условием. |

Нельзя оставлять квест без этапов или этап без условий завершения.

## 9. Карточка условия

Карточки в условиях появления и этапах имеют одинаковую структуру.

### 9.1. `Игровое событие`

| Значение в Inspector | Runtime-сигнал | Что означает | Обычный `targetId` |
|---|---|---|---|
| `Локация обнаружена` | `LocationDiscovered` | Дрон/система открыли локацию. | `Expedition_01` |

| `Точка локации исследована` | `AreaExplored` | Игрок посетил authored point of interest. | `ancient_terminal_01` |

| `Нападение на станцию началось` | `StationAttackStarted` | Контроллер волны объявил начало нападения. | `io_raid_01` |

| `Сканирование дроном завершено` | `DroneScanCompleted` | Дрон закончил цикл сканирования, независимо от новизны локации. | `Expedition_01` |
| `Антенной обнаружен сигнал` | `AntennaSignalFound` | Калибровка антенны закончилась успешным сигналом. | `Expedition_01` |
| `Погода изменилась` | `WeatherChanged` | Текущее состояние погоды стало `clear`, `cloudy` или `sandstorm`. | `sandstorm` |
| `Таймер завершён` | `TimerElapsed` | Gameplay-компонент подтвердил окончание именованного таймера. | `defend_station_180s` |
| `Пользовательское событие` | `Custom` | Расширение по стабильному Event ID для редкого authored-сценария. | `ancient_door_sequence` |

События намеренно не дублируют друг друга. Например:

- `Предмет получен` считает новые получения, а `Количество предмета` проверяет
  реальный инвентарь;
- `Система станции включена` относится к одному объекту, а
  `Питание станции восстановлено` — ко всей сети;
- `Враг уничтожен` считает отдельного противника, а `Нападение отражено`
  означает подтверждённый итог всей волны;
- `Локация обнаружена` является результатом прогрессии, тогда как
  `Сканирование дроном завершено` описывает выполненное действие и может
  произойти без новой локации.

### 9.2. `Какой объект`

`Конкретный объект по ID`:

- отображает поле `ID объекта`;
- принимает событие только с точно совпадающим стабильным ID;
- подходит для сюжетных локаций, конкретного предмета или исследования.

`Любой объект этого события`:

- поле ID скрыто;
- принимает любой `targetId` выбранного типа события;
- в условии появления объектного квеста именно этот `targetId` становится
  целью экземпляра.

`Объект, вызвавший этот квест`:

- доступен только в этапах объектного квеста;
- принимает событие только от сохранённого `targetId` этого экземпляра;
- не доступен в условиях появления, потому что до появления цель ещё не
  зафиксирована.

Пример: панель `station_solar_01` вызвала появление квеста. Условие этапа
`Объект, вызвавший этот квест` не завершится от ремонта
`station_solar_02`.

### 9.3. `Когда засчитывать условие`

Для событий, которые имеют сохраняемое состояние, Inspector предлагает два
режима:

| Режим | Поведение |
|---|---|
| `Только после нового события` | Игрок должен выполнить действие после начала отслеживания этого условия. Выполненное раньше не засчитывается. |
| `Если уже выполнено — засчитать сразу` | Если нужное состояние уже достигнуто, условие выполняется сразу. Иначе система продолжает ждать его выполнения. Состояние также восстанавливается после загрузки. |

Пример: если батарея уже включена до появления этапа, условие
`Система станции включена` в режиме текущего состояния выполнится сразу. В
режиме нового события игрок должен будет совершить новое включение.

Текущее состояние доступно только для фактов, которые проект действительно
умеет восстановить: обнаруженные локации, текущая локация, завершённые
исследования и квесты, condition объектов, состояния и уровни систем станции,
питание, заряд, количество предметов и погода.

У числовых условий `Количество предмета`, `Система улучшена` и `Уровень
заряда` всегда используется фактическое текущее значение.

### 9.4. `ID объекта`

Поле появляется для варианта `Конкретный объект по ID`.

ID должен совпадать с ID, который отправляет игровая система. Сравнение не
зависит от регистра, но рекомендуется копировать значение из исходного
конфига без изменений.

Типичные источники:

- `ExpeditionLocationData.LocationId`;
- `ItemData.ItemId`;
- ID `ResearchDefinition`;
- `IOEnemyConfig.EnemyId`;
- `StationObjectIdentity.ObjectId`;
- производные `MaintainableObject.ObjectId` и
  `StationDeviceInteractable.ObjectId`;
- station object ID из `StationSystems_Default`.

Для физического устройства ID задаётся один раз в `StationObjectIdentity` и
должен совпадать с `StationSystems_Default`. Компоненты обслуживания и
взаимодействия получают его с корня автоматически.
События включения/выключения системы отправляет `StationSystemsController` с
этим ID независимо от того, использовал игрок терминал или подошёл к устройству.
Для квеста на включение системы следует выбирать `Система станции включена`, а
не заполнять `Quest Interaction Id` у физической точки запуска.

Для двух глобальных источников ID подставляется автоматически и не требует
ручного ввода:

- питание станции — `station_power`;
- общий заряд — `station_energy`.

### 9.5. `Причина или тег (необязательно)`

Поле показывается для неисправностей, передачи предметов, нападений и
пользовательских событий.

Если поле пустое, принимается любая причина. Если заполнено, причина должна
совпасть со значением, переданным в fault API. Пример:

`EnemySabotage`

Ручное выключение Toggle и автоматическое отключение по недостатку энергии не
являются `StationFaultStarted`. Сигнал неисправности появляется при вызове
`DisableFromFault(...)`.

### 9.6. Пороги состояния объекта

Показывается только для событий состояния устройства.

Runtime хранит состояние в диапазоне `0..1`, а Inspector дополнительно
показывает процент:

- `0.35` = `35%`;
- `0.95` = `95%`.

Для появления квеста очистки обычно используется `не выше 35%`, а для
завершения — `не ниже 95%`.

### 9.7. Числовое сравнение

Для количества предметов, уровня улучшения и заряда доступны операции:

- `Меньше` (`<`);
- `Не больше` (`<=`);
- `Равно` (`=`);
- `Не меньше` (`>=`);
- `Больше` (`>`).

Примеры:

- иметь минимум 3 детали: `Количество предмета`, `Не меньше`, `3`;
- дождаться второго уровня батареи: `Система улучшена`, `Не меньше`, `2`;
- запустить аварийное задание ниже 20%: `Уровень заряда`, `Меньше`, `20%`.

### 9.8. `Сколько раз` / `Сколько объектов`

Минимум `1`. Условие завершится после накопления указанного количества
подходящих событий.

Примеры:

- уничтожить 5 врагов: `Враг уничтожен`, `Сколько раз = 5`;
- исследовать 3 точки: `Точка локации исследована`, `Сколько раз = 3`;
- получить один предмет: `Сколько раз = 1`.

Обычные runtime-системы отправляют прогресс по одному. `QuestSignalEmitter`
может отправить другое значение через поле `Amount`.

В режиме текущего состояния поле означает количество одновременно подходящих
объектов. У числовых условий оно скрыто, потому что нужное число задаётся через
сравнение и значение.

## 10. Настройка готовых сценариев

### 10.1. Первый квест: восстановление питания станции

Пример: `Main_RestoreBattery`.

| Поле | Значение |
|---|---|
| Повторяемость | `Появляется один раз` |
| Раздел журнала | `Основное задание` |
| Цель квеста | `Один общий квест` |
| Quest ID | `main.restore_battery` |
| Приоритет | `100` |
| Появление | `Игрок вошёл в локацию`, ID `Player_Station` |
| Завершение | `Система станции включена`, ID `station_battery` |

Новая игра начинает работу с выключенной батареей и обесточенной сетью.
Первое успешное взаимодействие с физической батареей через
`StationUpgradeableObject` восстанавливает сеть удерживанием `E` и отправляет
событие `StationSystemActivated` с ID `station_battery`. После восстановления
следующее короткое нажатие `E` открывает апгрейд батареи.

Не следует использовать ID `station_battery_01`: такого ID нет в
`StationSystems_Default`. Фактический ID батареи — `station_battery`.

Физическое восстановление отправляет событие и для старого сохранения, в
котором у батареи уже остался флаг `RequestedActive = true`. Выключать батарею
через терминал перед выполнением квеста не требуется.

Чтобы следующий вводный квест появился только после этого задания, в его
разделе `Когда появляется квест` нужно указать:

| Поле | Значение |
|---|---|
| Игровое событие | `После завершения квеста` |
| Какой объект | `Конкретный квест по Quest ID` |
| Quest ID | `main.restore_battery` |
| Сколько раз | `1` |

Указывается именно стабильный `Quest ID`, а не имя asset-файла и не
отображаемое название. Если условий появления несколько, завершение указанного
квеста считается одним из них; новый квест запустится после выполнения всех
условий списка.

### 10.2. Одноразовая сюжетная экспедиция

Пример: `Main_Expedition01`.

Общие настройки:

| Поле | Значение |
|---|---|
| Повторяемость | `Появляется один раз` |
| Раздел журнала | `Основное задание` |
| Цель квеста | `Один общий квест` |
| Quest ID | `main.expedition_01` |

Появление:

| Событие | Объект | ID |
|---|---|---|
| Локация обнаружена | Конкретный объект | `Expedition_01` |

Этапы:

| № | Задача | Событие | ID |
|---|---|---|---|
| 1 | Отправляйтесь в Ancient Outpost | Игрок вошёл в локацию | `Expedition_01` |
| 2 | Исследуйте Ancient Outpost | Враг обнаружен | `io_blue_weak` |
| 3 | Добудьте образец Blue IO | Предмет получен | `io_blue_shard_01` |
| 4 | Вернитесь на станцию | Игрок вошёл в локацию | `Player_Station` |
| 5 | Проанализируйте образец | Исследование завершено | `research_io_blue_shard_01` |

После этапа 5 повторное обнаружение `Expedition_01` не вернёт квест.

### 10.3. Повторяемая очистка солнечной панели

Пример: `Side_CleanSolarPanel`.

Общие настройки:

| Поле | Значение |
|---|---|
| Повторяемость | `Может появляться снова` |
| Раздел журнала | `Второстепенное задание` |
| Цель квеста | `Отдельный квест для вызвавшего объекта` |
| Название | `Очистите {targetName}` |

Появление:

- событие: `Состояние объекта упало ниже значения`;
- объект: `Любой объект этого события`;
- порог: `35%`.

Завершение:

- событие: `Состояние объекта восстановлено`;
- объект: `Объект, вызвавший этот квест`;
- порог: `95%`.

Если загрязнились две панели, появятся два независимых экземпляра. Повторное
сообщение о низком состоянии уже активной панели не создаст дубликат. После
очистки и нового загрязнения её квест появится снова.

### 10.4. Повторяемое восстановление турели

Пример: `Side_RestoreTurret`.

Появление:

- событие: `На станции возникла неисправность`;
- объект: `Любой объект этого события`;
- причина пустая — принимается любая fault-причина.

Завершение:

- событие: `Система станции включена`;
- объект: `Объект, вызвавший этот квест`.

Источник саботажа должен отключать объект через:

```csharp
StationSystemsController.Instance.DisableFromFault(
    StationSystemType.Turret,
    "station_turret_02",
    "EnemySabotage");
```

### 10.5. Повторяемая волна нападения

Для общей задачи «Отразите нападение IO»:

| Поле | Значение |
|---|---|
| Повторяемость | `Может появляться снова` |
| Цель | `Один общий квест` |
| Появление | `Враг обнаружен`, любой объект |
| Завершение этапа | `Враг уничтожен`, любой объект, нужное количество |

Пока квест активен, встречи с другими врагами не создадут дубликат. После
завершения следующая встреча сможет начать новую волну.

### 10.6. Исследование предмета в лаборатории

Для конкретного предмета можно использовать:

- появление: `Предмет получен`, конкретный `Item ID`;
- завершение: `Исследование завершено в лаборатории`, конкретный `Research ID`.

`Item ID` и `Research ID` могут отличаться, поэтому в таком этапе нужно выбрать
`Конкретный объект по ID`, а не `Объект, вызвавший этот квест`.

Текущий `ResearchController` отправляет `ResearchAnalyzed` только при первом
завершении конкретного исследования. Поэтому один и тот же `Research ID` не
подходит для бесконечно повторяемого задания. Повторяемый шаблон работает для
новых предметов/исследований с отдельными ID либо потребует отдельного
runtime-события повторного лабораторного анализа.

## 11. `QuestSignalEmitter` для authored-событий сцены

`QuestSignalEmitter` нужен, когда готовая игровая система ещё не отправляет
нужный факт. Например, игрок вошёл в точку интереса Ancient Outpost.

Поля компонента:

| Поле | Описание |
|---|---|
| `Signal Type` | Тип отправляемого квестового события. |
| `Target Id` | Стабильный ID факта или объекта. |
| `Target Name` | Имя для подстановки `{targetName}`. Если пусто, используется ID. |
| `Cause` | Дополнительная причина или тег для фильтра условия. |
| `Amount` | Сколько единиц прогресса добавить. Минимум 1. |
| `Value` | Числовое значение сигнала. Для процентов используется диапазон `0..1`. |
| `Emit On Start` | Отправить событие в `Start()`. |
| `Emit On Player Trigger` | Отправить при входе объекта с тегом `Player` в trigger. |
| `Emit On Player Exit` | Отправить при выходе объекта с тегом `Player` из trigger. |
| `One Shot` | Не отправлять повторно после первого вызова компонента. |

Для trigger-сценария на объекте должен быть корректно настроен Collider с
`Is Trigger`, а входящий объект должен иметь тег `Player`.

Метод `Emit()` можно вызвать из другого gameplay-компонента. Сигнал
обрабатывается только при наличии постоянного `QuestController`.

`One Shot` действует только в рамках текущего экземпляра компонента. Состояние
самого emitter сейчас отдельно в save не записывается. За защиту одноразового
квеста после загрузки отвечает история `QuestController`.

## 12. События, подключённые автоматически

| Событие | Источник |
|---|---|
| Обнаружение локации | `ExpeditionDiscoveryController` |
| Вход в локацию | `BootInitializer`, fallback `ExpeditionSceneBootstrap` |
| Выход из локации | `BootInitializer` перед сменой gameplay-сцены |
| Получение предмета | `WorldItem` |
| Удаление предмета и его текущее количество | `PlayerInventory` |
| Первое завершение исследования | `ResearchController` |
| Обнаружение и уничтожение IO | `IOEnemyController` |
| Изменение condition устройства | `MaintainableObject` |
| Физическое обслуживание и ручной запуск устройства | `StationDeviceInteractable`; результат запуска подтверждает `StationSystemsController` |
| Неисправность, включение, выключение и улучшение системы | `StationSystemsController` |
| Появление и потеря питания всей станции | `StationPowerController` |
| Текущий уровень общего заряда | `EnergySystemController` |
| Завершение сканирования дроном | `DroneScanController` |
| Обнаружение сигнала антенной | `AntennaController` |

`AreaExplored`, `ItemDelivered`, `StationFaultResolved`, события нападения,
таймер и `Custom` отправляются через `QuestSignalEmitter` или будущий профильный
gameplay-контроллер. Они не подменяются похожими событиями: например, обычное
удаление предмета не считается его передачей в конкретную цель.

Сигнал должен отправлять источник игрового факта. Не рекомендуется отправлять
его из HUD или кнопки журнала: UI не должен определять игровой прогресс.

## 13. Валидация

Внизу Inspector показывается один из статусов:

- `Конфиг квеста заполнен корректно.`;
- красное сообщение с первой найденной проблемой.

Проверяются:

- пустой `Quest ID`;
- пустое название;
- повторяемый квест без условия появления;
- объектный квест без условия появления;
- пустой элемент списка условий;
- конкретная цель без `ID объекта`;
- использование `Объект, вызвавший этот квест` в общем квесте;
- использование этой цели в условиях появления;
- отсутствие этапов;
- этап без условий завершения.

Каталог дополнительно проверяет:

- пустые ссылки на конфиги;
- одинаковые `Quest ID`.

Перед сборкой проект также проверяется через постоянный validator. Некорректный
квест или дубликат ID должен быть исправлен, а не проигнорирован.

## 14. Сохранение и изменение опубликованных квестов

`SaveGameData` версии 16 сохраняет:

- активные экземпляры;
- `Quest ID` и объектный контекст;
- индекс текущего этапа;
- прогресс каждого условия текущего этапа;
- частичный прогресс условий появления;
- историю и количество завершений;
- состояние обслуживаемых объектов;
- динамический чекпоинт отмеченного этапа и позицию игрока.

Правила безопасного изменения:

1. Не менять опубликованный `Quest ID` без миграции сохранения.
2. Не менять стабильные ID локаций, предметов и устройств без миграции.
3. Перестановка этапов меняет смысл сохранённого `currentStageIndex`.
4. Перестановка условий меняет соответствие сохранённого массива прогресса.
5. Удаление конфига приводит к тому, что сохранённый активный экземпляр не
   сможет быть восстановлен.
6. Тексты, приоритет и `Show In HUD` можно менять безопаснее всего: они не
   изменяют структуру прогресса.

До первого публичного релиза структуру можно свободно корректировать вместе с
очисткой тестовых сохранений. После релиза структурные изменения требуют
версии save и явной миграции.

## 15. Диагностика

### Квест не появился

Проверить:

1. Конфиг есть в окне `NERA Quests`.
2. Внизу Inspector нет красной ошибки.
3. Выбрано правильное игровое событие.
4. `ID объекта` совпадает с ID источника события.
5. Выполнено нужное количество условий согласно режиму `все` или `любое`.
6. Одноразовый квест уже не находится в истории завершений.
7. Для ручной точки сцены настроен `QuestSignalEmitter`.

После создания внешним инструментом нажать `Обновить список`, затем
`Синхронизировать каталог`.

### Квест появился для неправильного объекта

Проверить `Какой объект`:

- `Любой объект` намеренно принимает любой ID;
- для фиксированной цели выбрать `Конкретный объект по ID`;
- для ремонта того же объекта выбрать `Объект, вызвавший этот квест`.

### Квест не завершается

Проверить:

- активен ли нужный этап;
- выполнены ли условия этапа согласно режиму `все` или `любое`;
- не установлен ли `Сколько раз` больше ожидаемого;
- совпадают ли Item ID и Research ID с выбранными конкретными целями;
- для condition-события достигнут ли правильный порог;
- использует ли авария `DisableFromFault`, а не обычный Toggle.

### Квест появляется только один раз, хотя должен повторяться

Проверить:

- `Повторяемость = Может появляться снова`;
- после завершения действительно пришло новое событие появления;
- источник события сам поддерживает повторную отправку;
- для `ResearchAnalyzed` учесть, что текущее событие отправляется только при
  первом завершении конкретного исследования.

### В каталоге дубликат ID

Открыть оба конфига через поиск по ID и назначить одному из них новый стабильный
`Quest ID`, затем выполнить синхронизацию.

### Квест не виден в HUD

Проверить:

- включён ли `Показывать в HUD` в конфиге;
- активен ли сам квест;
- нет ли более приоритетного активного квеста той же категории;
- присутствует ли `QuestHUDController` на `HUD_Canvas/Quest_System`;
- назначены ли оба `background`, их дочерние `Content` и prefab-представления
  `P_QuestGroupView` / `P_Quest_Text`.

Компактный HUD динамически создаёт группы квестов: до трёх основных и до
четырёх второстепенных. Квесты с целью `Отдельно для вызвавшего объекта`
используют один общий заголовок и отдельную строку на каждый объект. Завершённая
строка сначала зачёркивается, затем исчезает; освободившееся место занимает
следующий активный квест по приоритету. Полный терминальный журнал пока не
реализован.

## 16. Финальный чек-лист автора

- [ ] Выбран правильный вариант повторяемости.
- [ ] Выбрана общая или объектная цель.
- [ ] `Quest ID` уникален и стабилен.
- [ ] Заполнены название и описание.
- [ ] Настроено реальное событие появления.
- [ ] Для конкретной цели указан правильный ID.
- [ ] Каждый этап содержит понятный текст и хотя бы одно условие.
- [ ] Для нескольких условий осознанно выбрано `все` или `любое`.
- [ ] Для объектного ремонта выбран `Объект, вызвавший этот квест`.
- [ ] Порог condition задан в процентах правильно.
- [ ] Внизу Inspector отображается успешная валидация.
- [ ] Каталог синхронизирован.
- [ ] Сценарий проверен в Play Mode и после Save/Load.
- [ ] После изменения runtime-кода запущены EditMode и PlayMode тесты.
